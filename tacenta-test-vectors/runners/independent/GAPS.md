# Gap report: building from tacenta-spec alone

A clean-room reader (`reader/`) was written from `tacenta-spec` and
`tacenta-test-vectors` only. This file records every point where the
specification was insufficient, ambiguous, internally inconsistent, or
disagreed with a vector.

Severity:

- **BLOCKING**: could not be implemented from the spec tree without guessing.
- **AMBIGUOUS**: more than one reading; a vector decided it, or nothing did.
- **MINOR**: wording, pointers, or a value that is findable but in the wrong place.

"Confirmed by vector V" means a hypothesis matched V. **It is still a gap.** A
second implementer without the vector would have had to guess, and some
hypotheses match only because the vector pins bytes a spec sentence does not.

Final run: 78/78 vectors PASS, 56/56 derived negative cases PASS, 0 SKIP.

---

## Whole tree

### G-01 No citable specification revision (MINOR)
- **Where:** `VERSION` (`0.0.0`), `CHANGELOG.md` (everything is under `[Unreleased]`).
- **Problem:** A conformance claim cannot name the spec revision it was built against. The vectors name model revisions ("generated by tacenta-model Vectors.lean") but no spec revision.
- **Resolution:** Not resolved. This reader is described as written against the tree as found.

### G-02 Normative content deferred to code, model, or scaffold pages (MINOR)
- **Where:** `README.md` ("the code, the model ... are the record"); `CONSTANTS.md` provenance cites `primitives/aead.rs`, `spqr/src/lib.rs`, `wire/src/lib.rs` and more; `protocol/error-handling.md` and `terminology.md` are scaffolds.
- **Problem:** Several facts are stated only as pointers into source files that are not part of the spec. No error taxonomy is specified, so whether a refusal is "malformed", "replayed" and so on, and what a caller sees, is unstated. Names such as `LastResortRecordFull` and `ReplayedLastResort` appear with no definition.
- **Resolution:** Not resolved. The reader uses one exception class per layer: `DecodeError`, `BundleRefused`, `RatchetError`, `SpqrError`/`ChainExhausted`.

## message-format.md

### G-03 Order of decoder checks is implied, not stated (MINOR)
- **Where:** Message type: "reject a bundle handed to it as a message on the type byte".
- **Problem:** The Rejection section lists what is refused but not in what order. The Message type section implies that framing is checked before lengths, but only for the bundle case.
- **Resolution:** Hypothesis: check version and type before any length check, in all three decoders. Tested by negative cases RM-13 and PB-02. No vector distinguishes the orders.

### G-04 The initial message's embedded `ratchet_message` versus the vectors (AMBIGUOUS)
- **Where:** Initial message: "The `ratchet_message` is a complete ratchet message".
- **Problem:** The spec says the field is a complete ratchet message that "still decodes on its own". The vectors in `serialization/initial-message.json` carry `dead` (2 bytes) and `00` (1 byte), which are not ratchet messages. The spec does not say whether the initial-message decoder validates the embedded message or refuses an empty one. Vectors and spec text point opposite ways.
- **Resolution:** By default the decoder does not validate the embedded message; this is the only reading under which the vectors decode. An opt-in strict mode (`validate_ratchet_message=True`) refuses a non-message (negative case IM-08). Decided by the vectors, against the most natural reading of the text.

### G-05 Initial-message refusals are not enumerated (AMBIGUOUS)
- **Where:** Initial message; Rejection; session-establishment.md Parameters: "a decoder that does not recognise the leading byte fails".
- **Problem:** The ratchet message and the bundle each get an explicit list of refusals; the initial message does not. Three things are open:
  - Whether `identity` and `ephemeral` must begin with the `EncodeEC` byte `0x05` at decode time. This is only implied by the generic `DecodeEC` sentence on another page.
  - Whether an empty `ratchet_message` is refused.
  - Whether `kem_ciphertext_len` is constrained. The vectors use 2-byte and empty ciphertexts, yet session-persistence.md requires `pending_initial`'s `kem_ciphertext` to be exactly one ML-KEM-1024 ciphertext, and says `encode_initial` "length-prefixes whatever it is given".
- **Resolution:**
  - Curve byte: hypothesis, refuse at decode (IM-05). All vectors use `0x05`, so they do not decide it.
  - Empty `ratchet_message`: accepted in the default mode.
  - Ciphertext length: unconstrained on the wire, as the vectors require.

### G-06 Bundle KEM key length check is implied, not stated (AMBIGUOUS)
- **Where:** Prekey bundle: "fails to decode under another".
- **Problem:** A length prefix alone lets a bundle carrying an ML-KEM-768-sized key (1,184 bytes) decode as a bundle. For it to "fail to decode under another" parameter set, the decoder must compare `kem_prekey_len` with the expected key length, and no refusal says so. The initial message (G-05) gets no such check, which is asymmetric.
- **Resolution:** Hypothesis: the bundle decoder takes the expected length (default 1,568) and refuses any other (PB-08). Bundles have no vectors.

### G-07 Which layer refuses a presence/identifier disagreement in a bundle (AMBIGUOUS)
- **Where:** Prekey bundle: "refused by the initiator before any agreement is computed"; session-establishment.md Sending the initial message.
- **Problem:** The sentence sits in the decoder's paragraph, among decoder refusals, but names the initiator. An implementer cannot tell whether `decode_bundle` refuses such a bundle.
- **Resolution:** Hypothesis: the decoder accepts it and `initiator_check_bundle` refuses it (PB-10). No vector.

### G-08 Identifier `0` in positions that cannot be absent (AMBIGUOUS)
- **Where:** Key identifiers: "The value `0` is reserved to mean **absent** and is never assigned".
- **Problem:** No refusal is stated for:
  - `signed_prekey_id = 0` or `kem_prekey_id = 0`, in a bundle or an initial message;
  - an initial message naming one-time id `0` whose bundle had a key.

  session-persistence.md refuses identifier 0 in a stored prekey store, but nothing is said for the wire.
- **Resolution:** Not resolved. The reader accepts these on the wire. No vector.

### G-09 Vector field names and header-size wording differ from the spec (MINOR)
- **Where:** `composite.json` and `message-encoding.json` inputs; message-format.md "The classical 40-byte header" versus triple-ratchet.md "the Double Ratchet's forty-two".
- **Problem:**
  - The vectors name the codeword field `chunk_data`, where the spec calls it `chunk`.
  - The vectors flatten presence, index and data into three independent inputs, so an "absent codeword with non-zero index" is representable as a vector input even though it has no encoding.
  - The 40/42-byte figures are reconciled only in triple-ratchet.md (2 + 40).
- **Resolution:** The runner maps `chunk_data` to `chunk`, and it fails a vector whose absent codeword has non-zero inputs (none do).

### G-10 The AEAD is not specified anywhere (BLOCKING)
- **Where:** ratchet.md Derivations: "which the AEAD (see message-format) then uses"; message-format.md never defines it. ratchet.md Sources describes only the published recommendation. CONSTANTS.md gives only a 32-byte tag.
- **Problem:** Unspecified:
  - which of the expanded keys and the IV go where;
  - the padding;
  - the exact HMAC input (AD then ciphertext? with lengths?);
  - where the tag sits (appended to the ciphertext?).

  The cross-reference points at a page that does not contain the definition.
- **Resolution:** Not resolved; not attempted. There are no AEAD vectors, and AES is not in the standard library.

## ratchet.md

### G-11 Ratchet initialisation is not described (BLOCKING)
- **Where:** ratchet.md as a whole. The conformance manifest credits "Session initialisation" to ratchet.md "Sending and receiving", but that section has no initialisation.
- **Problem:** Nothing says how Alice and Bob build their first states: which party derives a sending chain, whether `RK = SK` for the receiver, or which DH output is used. The only hints are in `ratchet-vector.schema.json` ("dh_ab is DH(alice_initial, bob_pub)") and triple-ratchet.md ("Bob's signed prekey continues to serve as his initial ratchet public key").
- **Resolution:** Hypothesis H, following the published Double Ratchet specification that ratchet.md names as its source:
  - Alice: `DHs` = her pair, `DHr` = Bob's key, `(RK, CKs) = KDF_RK(SK, dh_ab)`, `CKr` empty.
  - Bob: `DHs` = his pair, `DHr` empty, `RK = SK`, no chains.

  Confirmed by all four `ratchet/double-ratchet.json` vectors and `ratchet-reject.json`.

### G-12 Where the `info` strings are recorded is stated inconsistently (MINOR)
- **Where:** ratchet.md Derivations: the strings "are pinned in the conformance manifest ... determined by black-box research"; CONSTANTS.md: `RK_INFO`/`MK_INFO` are tier `ours`, free choices; the conformance manifest defers to CONSTANTS.md.
- **Problem:** ratchet.md points at the wrong document and describes the wrong provenance, since message-layer interoperability is not attempted.
- **Resolution:** Used CONSTANTS.md's `Tacenta RK` and `Tacenta MK`; confirmed by `double-ratchet.json`.

### G-13 Message-key expansion lengths and order are only in the vector schema (MINOR)
- **Where:** ratchet.md Derivations: "into an AES-256 key, an HMAC-SHA256 key, and a 16-byte IV".
- **Problem:** The spec does not state the HMAC key width, the total output length (80), or the split order; only `ratchet-vector.schema.json` says "80 bytes split 32/32/16". "A zero-filled salt" gives no length. That is harmless, since HMAC zero-pads short keys, so every zero salt up to 64 bytes gives the same result, but nothing in the text says so.
- **Resolution:** Schema's enc(32) ‖ mac(32) ‖ iv(16), with a 32-byte zero salt. Confirmed by every `message_keys` entry in `double-ratchet.json`.

### G-14 "Up to the header's counts" in the DH ratchet step (AMBIGUOUS)
- **Where:** The Diffie-Hellman ratchet, step 1: "Store any skipped message keys ... up to the header's counts".
- **Problem:** The plural "counts" names neither `PN` nor `N`. The published algorithm skips the old chain to `PN`.
- **Resolution:** Hypothesis: skip the old chain up to `header.pn`. **No vector decides this:** in `peer-revisits-ratchet-key` (pn = 5) the expected message keys are identical under either reading. Negative case DR-02 tests only the reader's own choice.

### G-15 Ratchet behaviour at the edges (AMBIGUOUS)
- **Where:** ratchet.md State ("either possibly empty"), Sending and receiving, Skipped keys.
- **Problem:** Not stated:
  - (a) what sending with an empty `CKs` does (a receiver before its first receive);
  - (b) what a header on the current chain with `n < Nr` and no stored key does (a duplicate). The published algorithm derives a wrong key and relies on the AEAD to fail;
  - (c) whether a rejected receive leaves the state unchanged;
  - (d) whether `MAX_SKIP` is enforced against `PN` when there is no receiving chain;
  - (e) how the `MAX_SKIPPED_STORE` check counts a key that replaces an existing map entry.
- **Resolution:** Reader policy, none decided by vectors:
  - (a) and (b) refuse;
  - (c) receives are transactional;
  - (d) `MAX_SKIP` is checked regardless of whether a chain exists;
  - (e) the check is against the resulting size.

  Tested by DR-03, DR-04 and DR-05.

### G-16 `MAX_SKIPPED_AGE` expiry boundary (AMBIGUOUS)
- **Where:** ratchet.md Skipped keys; key-deletion.md: "The boundary is pinned on both sides, in the model and in the core".
- **Problem:** The boundary is pinned in the model and the core, not in the spec. Unstated:
  - whether "outlived 1000 received messages" means `>` or `>=`;
  - whether `stored_at` is the clock before or after the storing receive increments it;
  - whether consuming a stored key counts as an accepted receive.
- **Resolution:** Hypothesis: `stored_at` = the clock before the increment; drop when `events - stored_at > 1000`; every accepted receive, including a stored-key hit, ages the store. No vector exercises expiry. DR-06 tests only this reader's boundary.

## sparse-pq-ratchet.md

### G-17 How `PROTOCOL_INFO` and a suffix are joined (AMBIGUOUS)
- **Where:** Derivations: "HKDF-SHA256 with `PROTOCOL_INFO` followed by its own suffix as `info`"; CONSTANTS.md suffixes `"Chain Start"`, `"Root"`, `"Chain"`; `SPLIT_INFO` "Suffix pattern copied from §5.2's".
- **Problem:** No separator is stated. CONSTANTS.md is internally inconsistent here: it says `SPLIT_INFO`'s `":Split"` copies §5.2's suffix pattern, which implies a leading colon, while the §5.2 suffixes it lists for the sparse ratchet carry no colon. The Braid suffixes do carry one.
- **Resolution:** Hypothesis: plain concatenation (`"Tacenta SPQRChain"`), confirmed by `post-quantum/spqr.json`. Separators `" "`, `":"`, `"_"` and `"-"` were tried and did not match. Only the chain step is pinned. Applying the same joining to `"Chain Start"` and `"Root"` is unverified. The vector pins the 64-byte output, not the next-chain-key/message-key split order (the spec states that order).

### G-18 The sparse ratchet state machine is under-determined (AMBIGUOUS)
- **Where:** Sending, Receiving, Retiring old epochs; session-persistence.md leaf rules.
- **Problem:** Not stated:
  - which counter value is fed to the chain step for a send, and carried as `pq_n` ("chains number from one" suggests the message's own number, starting at 1);
  - what "the epoch the agreement named" is in terms of Braid state;
  - what receiving for an epoch not yet reached does.

  The retention rule (`e <= epoch < e + EPOCHS_KEPT`) appears only in session-persistence.md's semantic rules, not on this page.
- **Resolution:** Implemented with the message's own number (first = 1), the retention predicate taken from session-persistence.md, and refusal for an unknown epoch. **No vectors drive this state machine**, so the reader's SP-01..SP-07 cases check only self-consistency.

## triple-ratchet.md

### G-19 `split_secret` is not specified (BLOCKING)
- **Where:** Initialisation: "the shared secret is expanded into two by a key derivation"; session-establishment.md; CONSTANTS.md `SPLIT_INFO`.
- **Problem:** Only the `info` constant is given. Unstated:
  - the salt;
  - the IKM;
  - the output length;
  - **which half initialises which ratchet**.
- **Resolution:** Hypothesis: `HKDF(salt = 32 zero bytes, IKM = SK, info = SPLIT_INFO, 64)`, confirmed by `post-quantum/split.json`; an empty salt is equivalent. **Half assignment not resolved:** the vector pins the 64-byte string only.

### G-20 Combined key length and how it is used (AMBIGUOUS)
- **Where:** What the combination must be: "an output the AEAD's key length"; ratchet.md: a message key "becomes one of two inputs to the encryption key".
- **Problem:** The AEAD consumes an 80-byte expansion of a 32-byte message key, so "the AEAD's key length" could be 32, 64 or 80. It is also unstated whether the combined key then goes through the message-key expansion (`Tacenta MK`) or is used some other way.
- **Resolution:** 32 bytes, confirmed by `post-quantum/triple.json`. The downstream use is not resolved.

### G-21 Composing the session is not specified (BLOCKING)
- **Where:** triple-ratchet.md Sending and receiving; message-format.md Ratchet message; session-establishment.md ("initialises the ML-KEM Braid's authenticator from `SK` directly").
- **Problem:** Unstated:
  - how `pq_epoch` relates to `ag_epoch`;
  - how a Braid message maps onto `ag_type` and a single `(chunk_index, chunk)` codeword;
  - what `chunk_index` means;
  - how "from `SK` directly" initialises the authenticator (the published Braid spec's initial update at some epoch?);
  - what Alice's first ratchet key pair is.
- **Resolution:** Not resolved; not attempted.

## mlkem-braid.md

### G-22 Braid epoch key derivation is not in the tree (BLOCKING)
- **Where:** mlkem-braid.md: "This page does not restate the protocol"; CONSTANTS.md suffix `":SCKA Key"`, `PROTOCOL_INFO` `Tacenta_MLKEM1024_SHA-256`.
- **Problem:** The page defers to the published Braid specification, which is not in the tree. It gives the suffix and the protocol identifier but not the construction: salt, IKM, where the epoch goes, output length.
- **Resolution:** Hypothesis, from the structure of the published specification the page defers to: `HKDF(salt = 32 zero bytes, IKM = ss, info = PROTOCOL_INFO ‖ ":SCKA Key" ‖ epoch (8 BE), 32)`. Confirmed by `post-quantum/braid.json`.

### G-23 Ratcheted Authenticator is not in the tree (BLOCKING)
- **Where:** Same as G-22; CONSTANTS.md suffixes `":Authenticator Update"`, `":ekheader"`, `":ciphertext"`.
- **Problem:** Not given:
  - the update construction;
  - the order of the two outputs;
  - the MAC inputs for `":ekheader"` and `":ciphertext"`;
  - how the authenticator is initialised from the preshared secret.
- **Resolution:** Hypothesis: `HKDF(salt = root_key, IKM = key, info = PROTOCOL_INFO ‖ ":Authenticator Update" ‖ epoch (8 BE), 64)` → `root_key ‖ mac_key`, confirmed by `post-quantum/auth.json`. The vector pins the 64 bytes, not the split order. MACs and initialisation: not resolved, not attempted.

### G-24 GF(2^16) and the erasure code are not specified (BLOCKING)
- **Where:** What this implementation fixes: "Reed-Solomon over GF(2^16), as the specification recommends".
- **Problem:** Not given:
  - the reduction polynomial;
  - the byte encoding of field elements;
  - the mapping from codeword index to evaluation node;
  - the systematic layout (which indices carry data);
  - how a value is padded into 32-byte chunks and 16-bit symbols.
- **Resolution:** Polynomial `x^16 + x^12 + x^3 + x + 1` (`0x1100B`), inferred from `gf.json` vector `doubling-folds` (`0x8000 · 2 = 0x100b`) and consistent with all 18 gf/inv/interp vectors. Elements are 2 bytes big-endian (from the vectors). Lagrange interpolation is mathematics. Node mapping and chunk layout: not resolved (`interp.json` supplies explicit nodes).

- **Where:** Sending the initial message: "encrypted under `SK` (or a key derived from it) with `AD`".

- **Problem:** Unstated: the hash, the field encodings (raw or `EncodeEC`, length prefixes), and the field order.
- **Resolution:** Not resolved; not attempted.

## XEdDSA (CONSTANTS.md, ADR-0002, session-establishment.md Notation)

### G-27 Clamping before XEdDSA signing is not stated (MINOR)
- **Where:** session-establishment.md: "`Sig(PK, M, Z)` is an XEdDSA signature"; `xeddsa.json` ("secret is the X25519 private key").
- **Problem:** The vector secrets (`07…07`, `0b…0b`) are unclamped byte strings. XEdDSA revision 1 takes a Montgomery private scalar, and the spec does not say whether the 32 bytes are clamped first.
- **Resolution:** Hypothesis: clamp (RFC 7748 `decodeScalar25519`), then revision 1 `calculate_key_pair` / `xeddsa_sign`. Confirmed by the three signing vectors.

### G-28 The verifier's accepted set is defined by reference to a library (AMBIGUOUS)
- **Where:** ADR-0002: "Verification goes through ed25519-dalek's `verify_strict`"; CONSTANTS.md sign-bit row.
- **Problem:** The rules that are stated are:
  - `s < l`;
  - small-order `A` and `R` refused outright;
  - the sign bit is the top bit of `signature[63]`;
  - `u < p`.

  Everything else is defined only by pointing at a library: what "small order" means, whether a non-canonical `R` or `A` encoding is refused at decoding or only by byte comparison, and that `u = p − 1` (division by zero in `convert_mont`) is refused, which appears only in a vector comment.
- **Resolution:** Implemented from the stated rules plus the vector comments: small order means `[8]P` is the identity; a point encoding with `y ≥ p` fails to decode; `u + 1 ≡ 0` is refused. All 13 verify-only vectors pass. The normative text leaned on a library and the vectors decided the details.

## Not attempted, and why

- **ML-KEM-1024 (FIPS 203) and the incremental KEM interface.** Very large, and no vector needs it. The Braid's split of the KEM into `header`/`ek_vector`/`ct1`/`ct2` is not specified in the tree beyond byte lengths.
- **ML-KEM Braid state machine** (eleven states plus `Failed`), **erasure encoder/decoder, header/ciphertext MACs, authenticator initialisation.** mlkem-braid.md restates none of it and defers to a document outside the tree (G-21 to G-24).
- **AEAD** (AES-256-CBC with PKCS#7, HMAC-SHA256 tag). Unspecified (G-10), no vectors, and AES is not in the Python standard library.
- **End-to-end PQXDH handshake and session composition** (initial message processing, Triple Ratchet session, Braid). Needs the KEM, the AEAD, and G-19, G-20, G-21 and G-25. Implemented: the SK KDF, `AD`, DH1..DH4 with the non-contributory refusal, and bundle verification.
- **Session persistence formats, prekey store, last-resort replay record, rotation.** No vectors, outside the requested priorities, and the fingerprint is unspecified (G-26).
- **Group messaging.** The page is a scaffold.
- **Full JSON-Schema validation.** No schema validator in the standard library; the runner checks only the top-level shape (`schema_version`, `vectors`, `id`).

Implemented but pinned by nothing in the vector set: the sparse ratchet's initialisation, root step and state machine (G-17, G-18); the Double Ratchet's store bound, expiry and edge behaviours (G-15, G-16); every bundle refusal (no bundle vectors). These are covered only by `reader/negative_cases.py`, which tests the reader's reading of the text, not agreement with the reference implementation.
