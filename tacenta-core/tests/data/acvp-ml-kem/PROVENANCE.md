# NIST ACVP ML-KEM sample vectors: provenance

These files are test data. They are used by `tests/kem_acvp_vectors.rs` and checked by `tests/kem_acvp_provenance.rs`. Passing those tests is tested agreement with the sample expected answers below. It is not FIPS 203 certification or validation, not independent review and not a correctness theorem.

Source: the National Institute of Standards and Technology (NIST), Automated Cryptographic Validation Protocol (ACVP) server sample vector files.

## Test revisions and groups
The files carry these revision strings: key generation `FIPS203`; encapsulation and decapsulation `FIPS203` and `FIPS203-tr1`. Upstream's specification (draft-celi-acvp-ml-kem-01) says "FIPS203-tr1 indicates a new test revision against the same standard, FIPS 203": a newer test revision of the same standard, not a different algorithm edition. It adds a seed key format for decapsulation. Both revisions are vendored and used, and stay separately labelled in directory names, in the fixture's `revisions` keys and in the test names. Algorithm "ML-KEM", parameter set "ML-KEM-1024", `vsId` 42 in all.

Selected groups (`tgId`, cases, `tcId` range), all ML-KEM-1024:

|---|---|---|---|---|---|
| ML-KEM-keyGen-FIPS203 | keyGen | 3 | AFT | 25 | 51-75 |
| ML-KEM-encapDecap-FIPS203 | encapsulation | 3 | AFT | 25 | 51-75 |
| ML-KEM-encapDecap-FIPS203 | decapsulation | 6 | VAL | 10 | 96-105 |
| ML-KEM-encapDecap-FIPS203 | decapsulationKeyCheck | 11 | VAL | 10 | 146-155 |
| ML-KEM-encapDecap-FIPS203 | encapsulationKeyCheck | 12 | VAL | 10 | 156-165 |
| ML-KEM-encapDecap-FIPS203-tr1 | encapsulation | 3 | AFT | 25 | 51-75 |

The ML-KEM-512 and ML-KEM-768 groups are not selected. Field meanings, from the specification: `d`, `z` the key-generation seeds (FIPS 203 Algorithm 16); `m` the encapsulation randomness; `ek`, `dk`, `c`, `k` the encapsulation key, decapsulation key (expanded form), ciphertext and shared secret. All values are hex strings; lengths verified on every selected case are `d`, `z`, `m`, `k` 32 bytes, `ek` 1,568, `dk` 3,168, `c` 1,568.

Which decapsulation cases are valid and which have a modified ciphertext (implicit rejection), and which key-check cases are valid, appears only in upstream's `internalProjection.json` as a `reason` field; the fixture carries it. In each decapsulation group 5 cases are "valid decapsulation" and 5 "modified ciphertext"; in each key-check group 5 are valid and 5 not ("noisy linear system values too large" for encapsulation keys, "modified H" for decapsulation keys). Those labels are UPSTREAM'S, not independently established classifications: this repository's tests do not check why a ciphertext or key was modified or whether it differs from a valid one. A decapsulation test establishes that the implementation returns upstream's expected `k` for the given `dk` and `c`; a key-check test establishes that its answer equals upstream's expected `testPassed`. The tests check only the number of cases carrying each label.

## Extraction
`extract.py` (standard-library Python) selects the groups above, joins each case's inputs from `prompt.json` to its expected outputs from `expectedResults.json` by `tgId` and `tcId`, adds `reason` from `internalProjection.json`, checks field lengths, checks that `internalProjection.json` carries the same input and output values, and exits non-zero if a selected group is missing or empty, a case has no expected answer, or an unselected group appears. Output is canonical JSON (sorted keys, compact separators). No value is computed or altered; the fixture is a re-arrangement.

Reproduce, from this directory:

    python3 -I extract.py original mlkem1024-acvp-fixture.json

Run again, the output is byte-identical. `tests/kem_acvp_provenance.rs` does the same extraction in Rust over the vendored originals and requires byte equality with the vendored fixture.

## Tests and what is not exercised
`tests/kem_acvp_vectors.rs` runs the key generation, encapsulation, decapsulation and key-check groups above through the standard ML-KEM-1024 API of libcrux and through the incremental interface of `tacenta-kem`; its header says which comparisons are direct against these expected answers. Not exercised: the `FIPS203` and `FIPS203-tr1` expanded-format decapsulation groups through the incremental interface, because `tacenta-kem` has no constructor from a FIPS 203 decapsulation key (its seed-format group is exercised instead); and key-check steps beyond the encapsulation-key modulus check and the decapsulation-key hash check.
